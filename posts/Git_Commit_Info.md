## 为什么要注意`Commit`格式？

**为了让别人和以后的自己看明白**。

你每一次 `git commit` 都要简述你此次提交的改动，如果描述太随意，以后想回溯历史版本的时候得费很大劲。

还有一个原因……

那就是 **能显得专业**。当然这是次要的。

---

## 怎样的提交信息看起来更舒服？

**简明扼要**。

- 首行控制在50个字符以内，抓要点，抓重点。
- 用祈使句描述 **做了什么**，而不是讲代码怎么写的。
- 着重解释 **本次提交的目的或原因**，例如我本次提交新添加了 `README.md`文件，我本次提交新增了 `XX`功能，我本次提交修复了 `XX` BUG。

如果你有看过别人项目的 `Commit` 信息，你应该会发现，有一种 **范式**。

1. 标题：`<提交类型>(<影响的文件或模块>): <简短描述>`。常见的提交类型如下：

| 提交类型            |      说明      |
| --------------- | :----------: |
| `feat(feature)` |     新增功能     |
| `docs`          |     修改文档     |
| `style`         |    代码格式修改    |
| `refactor`      |     代码重构     |
| `perf`          |   提升性能的改动    |
| `test`          |  增加或修改测试用例   |
| `chore`         | 构建过程或辅助工具的变动 |

2. 主题内容：对标题中的简短描述进行展开说明，详细解释 **为什么做这个修改**，指出和旧版本逻辑的不同之处（虽然 GitHub 代码仓库能够明显的看到，但是说明一下也无妨）

---

## 总结

信息是用来让人看的，让人看懂最重要，你可以有自己的提交格式，只要让人 **懂你意思**就行。
